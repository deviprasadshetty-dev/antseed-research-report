Technical Evaluation

Reverse API Engineer — how it works and where it fails

A concise read of the operating model, followed by the concrete failure modes observed across seven targets of varying difficulty.

RAE v0.14.0 OS Windows Python 3.12 Node 24 Browser Chromium-based, headless 7 targets Verified 2 / 7

01How it works

RAE is a Python CLI that wraps an LLM agent around a real browser session. It runs in two phases separated by a HAR capture.

STEP 2

STEP 4

STEP 6

What it needs to succeed

  • A browser session that reaches content the model can see
  • Network traffic that contains the actual data endpoints
  • No bot check, login wall, or CAPTCHA on replay
  • Client state (cookies, tokens, client versions) that is still valid

How it chooses what to do

  • Agent mode is autonomous; manual mode lets you browse.
  • Browser control comes from a browser MCP or a browser CLI.
  • The configured SDK/model does all analysis and code generation.
  • There is no "bring your own agent/model" mode.

What it emits

  • A typed client file and a README per run
  • A HAR capture of the browser session
  • A JSON result with status, paths, usage, and error kind
  • Exit codes: 0 success, 1 runtime error, 2 misuse
The contract in one line: RAE reports that a client was generated. It does not prove that the client works. That distinction is the source of most failures below.

1. It reports success without verifying the client works

Two of the three "ok" runs produced clients that did not fulfil the task. YouTube's client executed without exceptions, so the run passed — but every API call returned an error object and zero results parsed.

Guide response keys: ['error'] ...
No results parsed (response may be empty or format changed).
Log event response keys: ['error']
Root cause: the pass criterion is "the script ran", not "the script returned the requested data".

2. It can silently switch to a different target

Asked to reverse-engineer a JS-rendered quotes sandbox with no API, the model generated a client for an unrelated quote API instead. It ran successfully — against the wrong site. Pagination later crashed with a connection reset.

=== Page 1 Quotes ===
Retrieved 50 quote(s)          # wrong domain
=== First 3 Pages Combined ===
requests.exceptions.ConnectionError: Remote end closed connection without response
Root cause: when the requested site lacks a discoverable API, the model fills the gap with a plausible substitute instead of scraping the rendered page.

3. Bot detection breaks replay

On Pinterest, RAE correctly found the search endpoint and reconstructed the URL-encoded JSON payload and media schema. Replaying it outside the browser returned HTTP 403, with bot-detection flags in the response metadata. The session then timed out and exited 1.

GET /resource/BaseSearchResource/...   -> 403 Forbidden
metadata: is_bot / is_perf_metrics_bot  -> true
session ended with ReadTimeout
Root cause: endpoint discovery succeeds, but the request cannot be replayed without the browser's fingerprint and live session.

4. Auth walls leave nothing to discover

On social and community sites, the logged-out browser rendered only a shell with a sign-in prompt. No pins, no posts, no media URLs. On one site the agent hit a CAPTCHA immediately and the solve attempt timed out.

Root cause: no logged-in profile or session handoff; the capture contains only unauthenticated page chrome.

5. Internal API state goes stale

YouTube's Innertube endpoints were identified and documented correctly, but the hardcoded client version and missing session/visitor data made every call fail. This class of API rotates constants frequently, so a capture-time snapshot decays quickly.

Root cause: the generator freezes client fingerprints at capture time instead of deriving them at runtime.

6. HTML-based targets return nothing

On Amazon search, RAE correctly recognised server-rendered HTML and wrote a BeautifulSoup scraper, but the run ended in a timeout and the generated client returned zero results. Hardcoded session cookies appeared fabricated.

Searching for: mechanical keyboard
Found 0 results:
Root cause: anti-bot blocking plus selector drift, with no fallback verification against the live page.

7. Credentials leak into generated source

The Pinterest client hardcoded live session cookies directly into the file. The Amazon client hardcoded invented session identifiers. Either pattern is unsafe to commit or share.

Root cause: no secret scrubbing or environment-variable indirection in the code-generation templates.

8. Local tooling adds non-deterministic failures

  • Two browser MCPs collided over one browser profile: Browser is already in use.
  • The MCP file sandbox rejected a temp path: File access denied.
  • When the capture used a non-default browser driver, har_path came back null.
  • Redirected stdout stayed empty until exit, preventing live monitoring.
  • The free-tier model was rate-limited mid-run, causing retries and timeouts.

04Bottom line

It works when the target exposes an open, unauthenticated JSON API and the browser can see that traffic: it finds the endpoint, rebuilds the request, and emits a working client in about two minutes.

It fails when correctness depends on anything beyond that: bot detection, login walls, CAPTCHAs, rotated client state, HTML structure, or the model's own judgement about which site it is looking at. In those cases it still produces an artifact and often still reports status: "ok".

Practical reading: a useful reconnaissance and scaffolding tool for public APIs; not a reliable generator for protected or stateful targets, and not a substitute for executing the generated client.
